# Windows model UI E2E

`pnpm --filter @linkshell/windows test:model-ui-e2e` runs only on a disposable Windows GitHub Actions runner after a standalone bundle has been built. The dispatch-only workflow stage runs independently of the update E2E result. It does not publish a release.

The harness copies the bundle into its own temporary directory and downloads the official Windows Codex CLI 0.162.1 from npm, checking its pinned SHA-512 integrity. It uses that archive's `package/vendor/x86_64-pc-windows-msvc/bin/codex.exe` and checks the binary and working directory before launch. Electron, the bundled Host, the official agent, their profiles and their working directory are all isolated. Child processes receive an environment allowlist, an empty `CODEX_HOME` and `cli_auth_credentials_store = "file"`. Native `account/read` must confirm `account: null` and `requiresOpenaiAuth: true`.

The actual Electron UI chooses a model from the live catalog, sends the real `agents.models` preview request and creates a session with an empty prompt. The harness then changes that session's model through the composer. It requires all of:

- The actual `sessions.setConfig` request and successful response.
- The Host's `ls_config` notification with the selected value.
- The matching model in the SQLite `driver_state` override and latest persisted configuration event.
- The same checked UI value after leaving and reopening the session, and again after reloading the renderer with the original Host and app-server still running.

A fixture imported only into the copied CLI observes the real official agent's stdio without replacing any response. It records native `account/read`, `model/list` and the empty `thread/start` result. It rejects `turn/start`, `turn/steer`, `review/start`, `thread/compact/start` and `command/exec` before forwarding them to the native process; the final zero-inference assertion checks that same set of methods. No prompt, review, compaction or inference is required or allowed. The Codex global model configuration remains unchanged.

This proves model discovery, option writes, disk persistence and UI reopening. It does not prove account model entitlement, completed inference, or recovery of an empty native thread across a Host restart; an empty thread may have no rollout yet.

The same visible Electron window also exercises the production editing context menu. CDP enters and selects synthetic text. Before each real right click, the separate PID-scoped `native-menu-uia.ps1` finishes loading UIA and acknowledges readiness. After the click and matching Chromium context flags, a process-specific trigger starts its bounded search. It enumerates the target process's visible popup HWNDs with Win32, reads their UIA elements with `FromHandle` and invokes the native `MenuItem` named Copy, Cut, Paste or Undo. This avoids relying on the desktop UIA root exposing owned popup windows as immediate children. It never searches the main BrowserWindow's descendants. It records the actual invocation method: UIA `InvokePattern`, or a native MSAA default action whose name, role, window owner and bounds match that menu item. Each operation must change the textarea or clipboard as expected; Undo must reverse the preceding Paste. `Menu.popup`, menu roles and editing methods are never intercepted or called directly. The copied fixture hook only observes Chromium context flags and snapshots, seeds, reads and restores the clipboard. It uses Electron 44's asynchronous `read`, `ClipboardItem.getType`, `readText` and `writeText` APIs, and synchronous `clear`; operations are serialized. It refuses non-text formats or multiple items before modifying the clipboard, materializes the original plain text only in main-process memory and awaits verified restoration before process cleanup. A native quit also waits for restoration. No prompt is submitted.

Artifacts contain only allowlisted RPC/native fields, native menu invocation receipts, editing equality checks, scoped renderer screenshots and a report. They exclude credentials, original clipboard contents, environment dumps, connection URLs, tokens, raw agent output, profiles and databases. Cleanup terminates only processes whose executable resolves inside this run's temporary root, then removes that root. The staging bundle is preserved for subsequent CI steps.

Native window discovery requires the target PID and a visible `WS_POPUP` HWND. A Chromium container additionally requires a same-process `GW_OWNER`, `WS_EX_TOOLWINDOW`, and a UIA Window, Pane or Menu root; explicit UIA Menu roots and Win32 `#32768` menus retain their native menu path. The exact enabled, visible MenuItem and HWND ownership are checked again before invocation. Readiness has a 60-second startup limit, followed by a 30-second trigger limit and a separate 30-second menu search. The driver retains the helper's own process handle for cancellation, waits for it to exit and removes the per-action handshake files.

## Verified Windows run

[Run 41070067835](https://github.com/LiuTianjie/LinkShell/actions/runs/41070067835), commit `4ca4cc9229a31aacc41f7e33295be9c440b2a3bc`, passed the original five model scenarios on 2026-10-30. The official Codex returned an unauthenticated account and its live model catalog. The UI selected `gpt-6-astra`, created a real native thread with zero turns, and saved `gpt-6.1-sol` through `sessions.setConfig`; the Host event, database override and reopened/reloaded UI matched. The Host and app-server PIDs were unchanged. All 44 native records were independently checked: zero requests for each of the five forbidden methods, and zero `forbidden-request` events.

The sixth scenario failed before invoking Copy: Chromium reported an editable context with Copy, Cut, Paste and Undo enabled, but the helper completed its 22.3-second cold start after the menu had opened and then found no popup in 30 seconds of UIA root-child searching. Its receipt has no candidate or invocation method; none of the four native menu actions is proven by this run. The artifacts cannot distinguish a closed popup from an owned popup omitted by that enumeration. Both the restoration event and cleanup report confirm `clipboardRestored: true`; the temporary fixture was removed with no cleanup errors. The readiness handshake and HWND enumeration described above address those harness gaps and await Windows execution.

The source review uses [Electron 44.9.3's pinned Chromium 152.0.7977.167](https://github.com/electron/electron/blob/v44.9.3/DEPS#L4-L5). Chromium [attaches a child Widget's accessible root to an ancestor Widget](https://github.com/chromium/chromium/blob/152.0.7977.167/ui/views/accessibility/view_ax_platform_node_delegate_win.cc#L54-L66), so HWND top-level windows and UIA root children need not match. It also [assigns `Chrome_WidgetWin_` suffixes by registration order](https://github.com/chromium/chromium/blob/152.0.7977.167/ui/gfx/win/window_impl.cc#L139-L143); the suffix alone cannot identify or exclude a menu. These sources justify the harness correction, not a claim that the four native actions have passed.
