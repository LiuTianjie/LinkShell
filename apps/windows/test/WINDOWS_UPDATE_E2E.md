# Windows automatic update E2E

Run `pnpm --filter @linkshell/windows test:update-e2e` after `build:standalone` on a disposable GitHub Windows runner. An optional first argument selects one `artifacts/windows-stage-*/LinkShell` bundle. Without it there must be exactly one stage. The existing Windows workflow runs this only for `workflow_dispatch`; PR runs retain the native installer/junction regression tests.

The harness refuses other operating systems and environments without `GITHUB_ACTIONS=true`. It never runs against the staged source itself or an installed app. It copies the stage into random temporary directories and uses a separate home and Electron profile, including spaces and Chinese characters. It refuses to overwrite an existing Start Menu shortcut. Only the shortcut pointing to this test bundle is removed afterward.

The copied baseline and payload receive synthetic `65530.0.1` / `65530.0.2` versions. A copied-only Electron hook isolates userData and redirects the three exact official release URLs to a loopback fixture server. It records the actual native dialog and its returned response with one dialog ID, without choosing the result. Native accessibility activates the exact Chinese button inside the known PID's window. The harness requires that same real dialog to return the install response before waiting for the production updater's ready-file handshake. Installers compile the unchanged production C# UI and transaction with actual copied ZIP payloads.

A second copied-only hook observes the production `prepare-update`, `recover-update` and `stop-update-host` CLI commands. Synchronous start/exit records include command PID, exit code, the original Host PID and its liveness, recovery-marker presence, and app/owner/home path spellings with native physical app/owner paths. It neither replaces commands nor copies launch settings or marker contents. Both rollback and successful update require the actual preparation command to exit successfully with a recovery marker and the original Host process stopped; the later new-Host PID assertion remains separate.

The sequential lifecycle verifies:

1. A real bundled Node/CLI Host and Electron app report the baseline version.
2. Corrupt installer bytes fail the real checksum; the running Host PID is unchanged and no installer starts.
3. A valid installer containing a copied CLI that exits 74 only for `desktop --action recover-update` performs the real replacement, fails recovery, rolls back, and reopens the baseline through the native installer button.
4. Retrying with the normal payload installs and relaunches the new Electron app and Host, removes previous/failed bundles and clears the recovery marker.
5. Generated identity, machine, pairing fixture and home sentinel hashes stay equal. A synthetic session and its user/agent message events remain in SQLite and `PRAGMA integrity_check` returns `ok`.

The separate `installer-update.test.mjs` suite executes the native junction, ancestor-junction, missing-home, foreign-parent and handshake regressions on Windows. This harness does not claim live gateway pairing, signed release trust, production-account validation, real-agent turn continuity, a user's real Windows environment or WAN validation.

Before dependency installation, Windows CI also runs `installer transaction: shortcut-home`. It uses the production Unicode `IShellLinkW` / `IPersistFile` writer from an MTA worker, a real PE in a Chinese path, a uniquely owned temporary Programs subdirectory, and custom Home paths retaining their original spelling. An independent COM instance loads the saved `.lnk` and reads its raw target, working directory and arguments after both creation and overwrite. The original no-Home shortcut regression remains in the native suite.

Only `artifacts/windows-update-e2e` is uploaded for this harness: scenario results, compiler output, sanitized event records, PID-scoped UI diagnostics and window screenshots. Each native helper call also records its wall time, process error code/signal/killed state and last persisted phase in `<name>-call.json`; `<name>.json.progress.jsonl` checkpoints assembly loading, capture compilation, window lookup, inspection, capture and invocation before potentially blocking native calls. Home/profile contents, identity secrets, environment, database, copied bundles and installers are never copied into the report. Cleanup terminates only processes executing within the run's random directory, then removes that directory and its owned shortcut.

`native-uia.ps1 -AppProcessId <PID> -ButtonName '安装并重启'` invokes a native button. `-InspectOnly` reads the window and its immediate children without clicking or asking Chromium to build its entire accessibility tree. `-ScreenshotPath <PNG>` uses `PrintWindow` on a HWND whose owner PID is checked before and after; it never captures the desktop. `PrintWindow` can return a blank GPU/locked-session image. The JSON `screenshot.captured` field reports capture separately from button invocation. All calls have external process timeouts because native UI Automation and `PrintWindow` can block: the control-search budget has another 60 seconds for PowerShell/.NET cold startup and capture. The helper records startup, search and total elapsed time separately.

Electron's custom TaskDialog command links can appear as UIA `Pane`. The confirmation call adds `-NativeDialogTitle LinkShell` and requires the exact title, PID, `ControlType.Window`, nonzero HWND and native Win32 class `#32770` before searching inside that dialog. `InvokePattern` remains the first choice. If unavailable, only an actual `Button` HWND inside that dialog with `BS_COMMANDLINK` / `BS_DEFCOMMANDLINK`, the exact accessible name, MSAA push-button role 43, enabled/visible state and a nonempty localized default action may use `IAccessible.accDoDefaultAction`. This does not broaden matching to DOM panes. Reports record the actual action, dialog/target HWND and class, supported UIA patterns, native style, MSAA role/default action and owner validation. Confirmation screenshots use the dialog HWND; the owner app's image is not evidence of the modal's appearance.

Baseline and updated-window screenshots are supporting observations. Failure remains visible as `observations[].status = "unavailable"` and does not bypass any version, Host, rollback, identity or database assertion. The native install confirmation and rollback-reopen buttons must still report the exact PID and button with `clicked = true`; any invocation failure fails the scenario.

The automatic-update E2E stage in Windows CI [run `41077122254`](https://github.com/LiuTianjie/LinkShell/actions/runs/41077122254), validation SHA `28ed7146c070a57d21adbef740fade7d8a5a4809`, **passed all five scenarios and cleanup**. Both real confirmation dialogs returned install response `1`; the rollback-reopen button used the installer's native `UIA.InvokePattern` action. The baseline Host PID `8204` changed to `1412` after rollback, then to `6992` after a successful retry. The new Electron process was PID `5596`, and both App and Host reported fixture version `65530.0.2`. Recovery markers, identity/pairing fixture hashes, synthetic history, SQLite integrity and removal of previous/failed bundles passed their assertions. Both confirmation dialogs, the rollback-reopen window and the updated app window were captured and visually inspected. This records the update stage; the same run's model-selection and native-menu checks are assessed separately.

The command records also demonstrate the 8.3 ownership fix: preparation saw different `runneradmin` / `RUNNER~1` app-owner spellings with equal native physical paths, wrote a recovery marker, and exited successfully after the original Host process stopped. Both preparation cycles met the marker and process-exit assertions. The CLI compares native canonical paths and directory file identities while preserving the Home spelling used by named pipes.

The report records `status = "passed"`, `cleanup.temporaryFilesRemoved = true` and `cleanup.errors = []`. Cleanup reads the saved target through `shortcut-target.ps1`, using Unicode `IShellLinkW`, `IPersistFile.Load`, raw-path retrieval and UTF-8 output. It checks the first target against the copied executable's physical path, then independently rereads and requires an exact match before deleting only that shortcut. Cleanup failures still fail the run. The report confirms this guarded cleanup completed without errors; it does not publish a separate shortcut file inventory.

The preceding [run `41074267437`](https://github.com/LiuTianjie/LinkShell/actions/runs/41074267437), validation SHA `5e1aa378ac1c83530605a4b2aa02de408a1bfb61`, had passed all five update scenarios and the native Unicode shortcut preflight but failed during fixture cleanup. Its old WScript shortcut readback replaced Chinese target characters with question marks, so `realpath` returned `ENOENT` and the ownership guard refused shortcut deletion. The passing run changed only that cleanup fixture in the update path; no further production updater change was made after those five passing scenarios.
